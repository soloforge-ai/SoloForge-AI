# LNR-001 — LeadFlow Notification Reliability

Status: DONE — merged
Mode: SELF_REVIEW. Separate agent contexts were not used; no independent QA result is claimed.
Owner approval: 2026-10-02.
Objective: Ensure committed lead and decision states do not silently lose Telegram notifications.

## Scope
- Add a persistent SQLite notification outbox.
- Persist admin-new-lead and lead-status notifications before delivery.
- Use idempotent event keys for logical notification identity.
- Atomically claim PENDING → SENDING before sending.
- Recover stuck SENDING rows to PENDING on startup.
- Retry PENDING notifications in the background every 30 seconds.
- Stop automatic retry after 5 failed attempts and keep the row as FAILED.

## Exclusions
- No external queue/service.
- No Supabase/Postgres migration.
- No LeadFlow scoring changes.
- No SoloForge Flutter changes.

## Acceptance criteria and evidence
1. PASS: Failed admin notification remains durable and can be retried.
2. PASS: Duplicate event keys do not create duplicate logical notifications.
3. PASS: Delivery claim is atomic through PENDING → SENDING.
4. PASS: Stuck SENDING rows are recovered to PENDING on startup.
5. PASS: Owner notification is persisted before non-critical admin message updates.
6. PASS: Replayed decision callbacks do not notify twice.
