# LNR-001 — LeadFlow Notification Reliability

Status: DONE — merged
Mode: SELF_REVIEW. Separate agent contexts were not used; no independent QA result is claimed.
Owner approval: 2026-10-02.
Objective: Prevent committed lead/status changes from silently losing Telegram notifications.

## Scope
- Add a persistent SQLite notification outbox.
- Persist logical notifications before attempting Telegram delivery.
- Use idempotent event keys.
- Atomically claim PENDING → SENDING before delivery.
- Retry pending notifications every 30 seconds.
- Recover stuck SENDING rows to PENDING on startup.
- Stop automatic retries after 5 failed attempts.

## Exclusions
- No external queue/service.
- No Supabase/Postgres migration.
- No LeadFlow scoring changes.
- No SoloForge Flutter changes.

## Acceptance criteria and evidence
1. PASS: admin new-lead notifications persist before delivery.
2. PASS: lead owner APPROVED/REJECTED notifications persist before delivery.
3. PASS: failed Telegram delivery returns the outbox row to PENDING until max attempts.
4. PASS: SENT is recorded only after Telegram send succeeds.
5. PASS: event keys prevent duplicate logical notifications.
6. PASS: concurrent delivery is reduced by atomic claim PENDING → SENDING.
7. PASS: stuck SENDING rows recover to PENDING on init.
8. PASS: retry stops at FAILED after 5 unsuccessful attempts.
9. PASS: replayed admin callback does not notify twice.
10. PASS: LeadFlow Test, Graphify, Flutter analyze/tests and Android APK build passed on final head `a9ecee46bf0c09856406d237a70caed4f6d019b8`.
